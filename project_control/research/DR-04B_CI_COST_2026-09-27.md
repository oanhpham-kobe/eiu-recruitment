# DR-04B — CI Workflow and Repeat-Run Cost

Status: COMPLETE
Research date: 2026-09-27
Repository: `oanhpham-kobe/eiu-recruitment`
Technical evidence baseline: `8dcb0a5d7ce1be9d82e3448c01cdc1643e3ac8c4`
Parent research: `project_control/research/DR-04_DELIVERY_THROUGHPUT_2026-09-27.md`

## Question

Does exact-SHA governance require expensive repeated product verification, or can existing path-aware CI preserve safety at much lower cost for governance/evidence-only commits?

## Baseline workflow structure

### Integration CI

Baseline `.github/workflows/integration-ci.yml` already contains an impact resolver.

Default behavior:

- `web/*` => Web verification;
- `supabase/*` => DB verification;
- `recruitment_webapp/*` => Web + DB;
- `project_control/*`, governance workflow and agent/review metadata => no Web/DB verification;
- unknown or other `.github/*` changes => Web + DB.

Two mechanisms override impact resolution and force both Web + DB:

1. manual `workflow_dispatch` with `full_verification=true`;
2. commit message containing `[full-ci]`.

Full Web verification includes npm install/audit, design check, lint, typecheck, build, Playwright Chromium install and the web test set.

Full DB verification starts local Supabase, replays migrations from zero, runs cumulative SQL/concurrency regressions across accepted contracts, performs a second DB reset for standalone bulk replay, runs DB lint, then stops Supabase.

### Governance CI

Baseline `.github/workflows/governance-ci.yml` is separate and lightweight:

- checkout exact commit;
- Python 3.13 setup;
- install PyYAML;
- `validate_omp_native.py`;
- `validate_control_plane.py`.

Its purpose is materially different from product verification, so keeping Governance CI separate is reasonable.

## Representative runtime measurements

Wall-clock values below use GitHub Actions run/job timestamps. They measure elapsed gate latency, not exact billable-minute accounting.

### S08-001 — path-aware behavior works

Product integration `3070e56a`:

- Integration CI `35880657875`;
- commit contains `[full-ci]`;
- `15:19:10Z -> 15:23:42Z`;
- ~`4m32s`.

Governance CI `35880657901` on the same SHA: ~`11s` in run metadata.

Governance-only final-acceptance gate `0d8c5c2`:

- Integration CI `35882761018`;
- no `[full-ci]` marker;
- `15:36:08Z -> 15:36:17Z`;
- ~`9s`;
- impact resolution skips expensive Web/DB jobs because only governance/review evidence changed.

Governance CI `35882761149`: ~`1m12s` for that particular run.

**Finding:** S08 exact-SHA acceptance does not repeat full product CI. The existing workflow already supports cheap exact-SHA governance when the evidence-only commit is allowed to use impact analysis.

### S06-002 — explicit forced duplication

Application-verified integration `80146bc5`:

- commit `ci(s06-002): isolate standalone bulk replay [full-ci]`;
- Integration CI `34705140390`;
- `16:24:41Z -> 16:28:43Z`;
- ~`4m02s`.

Job timing:

- impact resolver ~`4s`;
- Web verification ~`1m25s`;
- DB integration ~`3m53s`.

DB infrastructure/setup dominates a large part of the job:

- local Supabase start ~`1m35s`;
- migration replay ~`31s`;
- S06-002 lifecycle concurrency test ~`38s`;
- second DB reset ~`30s`.

Final-gate SHA `5f2b76c7`:

- commit `chore(state): trigger exact S06-002 final gate [full-ci]`;
- commit diff itself is governance-only (`project_control/CURRENT_STATE.md`);
- its text records `80146bc5` as the latest application-verified integration and records the prior full Integration/Governance PASS;
- `[full-ci]` nevertheless overrides impact detection;
- Integration CI `34705634804`;
- `16:34:10Z -> 16:38:16Z`;
- ~`4m06s`.

Job timing on the governance-only SHA:

- impact resolver ~`6s`;
- Web verification ~`1m23s`;
- DB integration ~`3m55s`.

No product/runtime change justified re-executing those suites between the two SHAs; the second run closely reproduces the first.

**Finding:** S06 is direct evidence of expensive verification duplication caused by an explicit full-gate choice, not a limitation of Integration CI.

## Governance-policy reconciliation

Current baseline governance policy `AUTONOMY_PARALLEL_GOVERNANCE.md` already contains a verification-economy rule:

- on repair, rerun failed/affected checks and crossed shared-invariant checks, not unrelated suites;
- at final task acceptance, exact-SHA CI runs the **minimum domain-level acceptance set selected by changed/impacted domains**;
- unchanged unrelated domains remain closed;
- `[full-ci]` may be used only to broaden verification for an explicit slice-closing, shared-contract, or otherwise justified full gate.

This materially changes the diagnosis.

### What is current architecture vs historical/process behavior

- S07 and S08 follow the current verification-economy model correctly: product integration gets the broad verification appropriate to the change; later governance-only exact-SHA commits run impact resolution + Governance CI without rerunning unrelated product domains.
- S06 was a high-risk shared-contract task, so `[full-ci]` was *permitted* by policy. The inefficiency was **where the second full gate was placed**: after a governance-only state transition, immediately after the product integration had already passed a full gate.
- There is no separate acceptance GitHub workflow at the S06 SHA that mechanically inserts `[full-ci]`; the repository contained only Integration CI and Governance CI. The marker came from the coordinator/state-transition commit convention used at that time.
- By S07/S08, this behavior had already improved: governance-only final acceptance commits did not carry `[full-ci]` and therefore completed cheaply.

Therefore DR-04B does **not** recommend rewriting CI or removing `[full-ci]` support.

## Final DR-04B verdict

### KEEP

- separate Integration CI and Governance CI;
- impact resolver and fail-closed default for unknown paths;
- ability to request `[full-ci]` for actual shared-contract, slice-closing or explicitly justified full gates;
- exact-SHA acceptance CI;
- full DB replay for product SHAs that genuinely cross DB/shared invariants.

### KEEP / STANDARDIZE AS THE DEFAULT

For evidence/control-state-only commits after a green product integration:

1. run normal Integration CI impact resolution;
2. expect Web/DB to remain closed when only allow-listed governance paths changed;
3. run Governance CI on the exact governance SHA;
4. record provenance from the exact governance SHA back to the last green product SHA;
5. create the immutable checkpoint only after the exact governance SHA passes its applicable checks.

This is already demonstrated successfully by S07 and S08.

### LIGHTEN / PREVENT DUPLICATION

Do not put `[full-ci]` on a governance-only state/evidence commit merely to make it a new exact-SHA review target when:

- a directly preceding product SHA already passed the justified full gate;
- the diff is provably limited to governance/evidence paths;
- no workflow, product, migration, test, dependency, lockfile or build configuration changed;
- Governance CI validates the new control state.

If a high-risk task requires one final full shared-contract gate, place that gate on the last SHA containing the product/test changes. Subsequent evidence-only acceptance commits should use path-aware exact-SHA validation unless new source changes reopen product verification.

### AUTOMATE

Add or strengthen an exact governance-delta proof that records:

- last green product SHA;
- governance head SHA;
- complete changed-file list;
- classification `GOVERNANCE_ONLY | PRODUCT_AFFECTING | AMBIGUOUS`;
- whether `[full-ci]` is justified and why.

Fail closed to full CI for `PRODUCT_AFFECTING` or `AMBIGUOUS`.

This is a small policy/validator enhancement, not a CI architecture redesign.

## Correction to DR-04A provisional wording

The phrase “repeated governance tail” must distinguish two costs:

1. **cheap control/evidence serialization**, which still creates commits/reviews but can complete CI in seconds through impact analysis (S07/S08);
2. **expensive forced product re-verification**, observed in S06 when `[full-ci]` was applied to a governance-only exact-SHA transition.

Only the second is a significant CI compute/latency duplication. The first remains a process/commit-count optimization question for DR-04C.
