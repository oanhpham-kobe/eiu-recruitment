## Question

Does exact-SHA governance require expensive repeated product verification, or can existing path-aware CI preserve safety at much lower cost for governance/evidence-only commits?

## Baseline workflow structure

### Integration CI

Baseline `.github/workflows/integration-ci.yml` already contains an impact resolver.

Default behavior:

- `web/*` => Web verification;
- `supabase/*` => DB verification;
- `recruitment_webapp/*` => Web + DB;
- `project_control/*`, governance workflow and agent/review metadata => no Web/DB verification;
- unknown or other `.github/*` changes => Web + DB.

Two mechanisms override impact resolution and force both Web + DB:

1. manual `workflow_dispatch` with `full_verification=true`;
2. commit message containing `[full-ci]`.

Full Web job includes npm install/audit, design check, lint, typecheck, build, Playwright Chromium install and the complete web test set.

Full DB job starts local Supabase, replays migrations from zero, runs the cumulative accepted SQL/concurrency regression set across S04-S08 contracts, performs a second DB reset for standalone bulk replay, runs DB lint, then stops Supabase.

### Governance CI

Baseline `.github/workflows/governance-ci.yml` is separate and lightweight:

- checkout exact commit;
- Python 3.13 setup;
- install PyYAML;
- `validate_omp_native.py`;
- `validate_control_plane.py`.

Its purpose is materially different from product verification, so keeping Governance CI separate is reasonable.

## Checkpoint conclusion

The earlier broad statement that all post-product acceptance commits repeat expensive CI is too coarse and must be corrected.

The measured reality is:

1. **S07 and S08 are already efficient:** governance-only acceptance commits preserve exact-SHA checks while Integration CI returns in roughly 9–11 seconds because expensive product jobs are skipped.
2. **S06 is the problematic case:** a governance-only exact-SHA gate deliberately adds `[full-ci]`, causing another ~4-minute full run immediately after a ~4-minute full application run.
3. **The architecture needed for optimization already exists.** No new CI platform is required; policy can rely on the existing impact resolver plus a stricter proof of governance-only diffs.

### Candidate policy direction

For a post-product commit to reuse the last green product verification instead of forcing `[full-ci]`, require all of the following:

- diff from the recorded green product SHA is limited to an explicit allowlist such as `project_control/**` and immutable review/evidence artifacts;
- neither `.github/workflows/integration-ci.yml`, runtime code, migrations, tests, lockfiles nor build configuration changed;
- Governance CI passes on the new exact SHA;
- an automated verifier records the base product SHA, head governance SHA and exact changed-file list;
- accepted checkpoint/tag points to the governance head, while product-verification provenance points to the last green product SHA.

If any non-allowlisted path changes or proof is ambiguous, fall back to full Integration CI.

This preserves fail-closed behavior and exact-SHA governance while avoiding a second full product suite for evidence-only state transitions.
